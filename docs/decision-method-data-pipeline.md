# 決まり手データの取得・蓄積方針

## 現状確認（2026-11-26）

- `race_payout_results` には BOAT RACE DB の取得元 JSON を `source_data` として保存し、決まり手・1着登録番号・進入コースを解析結果として保持する。
- 現在確認できた保存済みレコードは1件で、2026-11-24の実データでは `race.kimarite` と `entries[].rank/regno/course` の組み合わせで正しく解析されていた。
- アプリ画面からの「結果・払戻を取得」操作で `sync-race-results` が呼び出される。結果公開だけで自動同期される構成ではない。
- `historical_racer_entries` の決まり手は、1着行に限定して履歴として取り込まれる。
- DBの拡張一覧には `pg_cron` がなく、`cron` スキーマのジョブ一覧も確認できなかった。現時点でDB内の定期実行基盤は確認できていない。
- GitHub Actions の既存検証ワークフローは push / pull request トリガーであり、データ取得ジョブではない。

## 自動取得を有効にする前に必要なこと

1. 定期実行の実行主体を決める。
   - Supabase Cron を利用する場合は、プロジェクトでの拡張有効化と安全な認証情報の保管が必要。
   - 外部スケジューラーを利用する場合も、呼び出し用の認証情報を安全に保管する必要がある。
2. 現在の `sync-race-results` はログインユーザーのJWTを検証する。匿名キーだけでの呼び出しや、サービスロールキーをログインユーザーとして扱う設計にはしない。
3. 日付・競艇場・レース番号を対象に、未取得または未解析のレースだけを処理する。再取得時は既存レコードを壊さない冪等性を維持する。
4. 取得失敗、未公開、解析不能を区別して記録し、決まり手が不明なレースを推測で補完しない。
5. 取得件数、解析成功率、未解析件数、最終取得時刻を監視できるようにする。

## 安全方針

- 本番のEdge Function、DBスキーマ、保存データはこの調査では変更しない。
- 本番への定期実行設定や秘密情報の追加は、実行方法・権限・費用を確認してから明示的な承認を得る。
- まず開発ブランチで取得対象の選定・再実行安全性・解析テストを整備する。

## 追加調査：重複防止とユーザー認証

- `race_payout_results` には UNIQUE 制約 `(user_id, race_date, venue_code, race_no)` が既にある。したがって同一ユーザー・同一レースの重複行はDB側で防止され、現在の `upsert` は同じキーを更新する。
- `sync-race-results` はJWTからログインユーザーを特定し、その `user_id` で保存する。よって、単純な共通スケジューラーから匿名リクエストを送る方式では動かない。
- 全ユーザーに共通のレース結果を一度だけ収集する方式と、ユーザーごとに保存する現在のテーブル設計は目的が異なる。自動化前にどちらを正式なデータ所有モデルにするか決める必要がある。
- サービスロールキーをブラウザーやアプリ画面に置く設計は禁止。サーバー側の安全な実行環境でのみ扱う。
- 既存テーブルには払戻組合せ・払戻金額・人気の列もある。将来の同期処理でこれらを不用意にNULL上書きしないよう、更新対象列を明示し、既存値保持のテストを設ける。

## 次の安全な実装順

1. 取得処理を「取得」「解析」「保存」に分ける。
2. 保存は既存の UNIQUE キーを使い、更新列を限定する。
3. 取得失敗・未公開・解析不能を別状態で記録する。
4. ユーザー単位か共通データ単位かを決定した後、認証を含むスケジューラーを設計する。
5. まず開発環境で少数レースを使って重複実行・再実行・既存払戻値保持を検証する。

## データ所有方式の判断メモ（2026-11-26）

### 現在のDB設計で確認できたこと

- `race_payout_results`、`historical_racer_entries`、`historical_motor_entries` はいずれも Row Level Security が有効。
- 3テーブルとも authenticated ユーザーに対する所有者単位のポリシーが設定されている。
- `race_payout_results` は `user_id` を含む一意キーを使用し、外部キーで `auth.users` に紐づく。
- 現時点の `race_payout_results` は1ユーザー・1行のみ。複数ユーザー運用時の負荷や重複は、実測できる段階にない。
- よって、現状は「ユーザーごとに保存する」構造であり、共通データベースとして使われているとは確認できない。

### 選択肢

| 方式 | 長所 | 注意点 |
| --- | --- | --- |
| A. ユーザー別保存を維持 | 既存アプリ・RLS・同期処理への変更が少ない。移行リスクが低い | 同じレース結果をユーザーごとに取得・保存するため重複が増える |
| B. 公開レース結果を共通保存 | 同じレースを一度取得すれば全ユーザーで再利用できる | 新しい共通テーブル、RLSポリシー、移行、読み取り処理の変更が必要 |
| C. ハイブリッド | 公開の公式結果・選手履歴は共通、ユーザー固有の予想・メモ・購入記録は個別に分離できる | 境界の設計と段階的な移行が必要。最初の実装量は増える |

### 暫定推奨

- 直近の安全な開発では A を維持し、既存データやアプリの挙動を壊さない。
- 将来の複数ユーザー展開を見据えた最終形は C を候補とする。公開情報と個人情報を分離でき、同一レースの重複取得を抑えられるため。
- ただし、Cへの移行は現時点では実施しない。アプリ全体のテーブル参照、RLS、Edge Function、履歴取込処理の依存関係を洗い出し、移行手順とロールバック方法を用意してから判断する。
- 現在の単一ユーザー・1行という実績だけで、複数ユーザー時の最適構成や負荷を断定しない。

### 追加で必要な設計確認

1. 予想・レース結果・払戻・選手履歴・モーター履歴のうち、どれが公開共有データで、どれがユーザー固有データか。
2. 共有データを全ログインユーザーに読み取り専用で公開する場合のRLSと、書き込みを許可するサーバー処理の境界。
3. 同じレースを複数ユーザーが同時に要求した場合の一意キーと取得競合制御。
4. 既存ユーザー別履歴を共通履歴へ移す際の重複排除、所有者データの保持、ロールバック。
5. 共有データの取得元・利用条件・更新頻度・障害時の再取得方針。

### 特に重要な発見

- `historical_motor_entries` は名前から想像する「モーター履歴」だけでなく、選手登録番号・実進入コース・着順・本番STも保存し、選手履歴の主な読み取り元として使われている。
- したがって、モーター履歴だけを共通テーブルへ移しても、選手のST・コース別成績はユーザー別のまま残る。共通化の単位はテーブル名ではなく、データ項目と取得元の意味で切り分ける必要がある。
- `historical_motor_entries` と `historical_racer_entries` は両方から同じ選手・レースのデータを読み、分析処理内でキーを使って重複を避けながら欠損項目を補完している。移行時に片方だけを共通化すると、この優先順位・補完ロジックを再設計する必要がある。
- 現行の各Edge FunctionはJWTでユーザーを認証し、`user_id` を条件に読み書きしている。共通データ方式に移す場合、サービス側の安全な書き込み経路と、ログインユーザー向けの読み取り専用ポリシーを別々に設計する。
- `import-racer-history-public` は現在のGitHubブランチにファイルがなく、以前に確認したデプロイ済み関数のソースと、ブランチで管理されているコードを同一視しない。バージョン管理へ取り込む前に、デプロイ済みソースとの照合が必要。

### 現時点の結論

共通化候補は、公開元から取得した「レース・艇単位の事実データ」（日付、場、R、艇、登録番号、実進入、着順、ST、決まり手、展示データ）とする。一方、ユーザー固有の予想、メモ、購入記録、設定は個人領域に残す。

ただし、展示データの取得範囲・再取得規則・提供元利用条件・既存履歴との優先順位が確定していないため、現段階ではテーブル分割やデータ移行を行わない。

## 制約・インデックス・列定義の確認（2026-11-26）

本番DBのカタログを読み取り専用で確認した。

### 現行の一意キーと検索インデックス

- `historical_motor_entries`: UNIQUE `(user_id,race_date,venue_code,race_no,lane)`。
  - 検索用: `(user_id,venue_code,motor_number,race_date DESC)`
  - 選手履歴用: `(user_id,racer_registration_no,race_date DESC)`（登録番号がNULLでない行）
  - レース検索用: `(user_id,race_date,venue_code,race_no)`
- `historical_racer_entries`: UNIQUE `(user_id,race_date,venue_code,race_no,lane)`。
  - 選手履歴用: `(user_id,racer_registration_no,race_date DESC)`
  - 場・実進入用: `(user_id,venue_code,actual_course,race_date DESC)`
- `race_payout_results`: UNIQUE `(user_id,race_date,venue_code,race_no)`。
  - 決まり手参照用: `(user_id,race_date,winning_racer_registration_no)`（決まり手がNULLでない行）
  - 日付・レース参照用: `(user_id,race_date DESC,venue_code,race_no)`

現状のユーザー別検索には対応するインデックスが存在する。共有化後は `user_id` が検索キーから外れる可能性があるため、共有テーブル向けの別インデックス設計が必要になる。既存インデックスをそのまま流用できるとは限らない。

### 列の意味に関する注意

- 両履歴テーブルに `actual_course`, `finish_rank`, `actual_st`, `actual_st_raw`, `actual_st_is_f`, `source_name`, `source_data`, `imported_at` がある。
- `historical_motor_entries` は `racer_registration_no` がNULL許容、`historical_racer_entries` は必須。
- `historical_motor_entries` には `motor_number` が必須で、展示計測項目（展示タイム、一周、直線、まわり足、展示ST）がある。
- `historical_racer_entries` には `decision_method` があるが、モーター履歴テーブルにはない。
- したがって統合先を単純な「選手履歴」または「モーター履歴」と名付けると、片方の意味を取り落とす。共有候補は「レース出走艇の事実データ」と「モーター展示計測データ」を論理的に分ける設計が自然。ただし現行テーブルは引き続き両方の情報を保持するため、移行時は旧列から新しい論理領域への対応表が必要。

### 暫定的な共有データのキー案

公開事実データ（艇単位）の候補キーは `(race_date, venue_code, race_no, lane)`。同じ艇番レーンの一走を一意に表すキーとして現行テーブルの一意キーから `user_id` を除いた形。ただし、これは設計候補であり、DB制約の追加や移行は行っていない。

モーター展示データも同じ一走に紐づくが、取得元・再取得時の更新規則が異なるため、同じ行に無条件で混ぜず、出典と取得時刻を項目単位で保持する。選手登録番号やモーター番号はレースごとに変わり得るため、キーの一部にはしない。

### 次の検証方針

旧テーブルから作る読み取り専用の統合候補を対象に、次の項目を同一キーで比較する。

1. レース出走艇の件数とキーの一意性。
2. 登録番号・実進入・着順・本番ST・F判定・決まり手の値とNULL件数。
3. モーター番号・展示タイム・一周・直線・まわり足・展示STの値とNULL件数。
4. 元データの取得元・取得時刻が追跡できる割合。
5. 既存分析で使用する対象日・対象場・選手登録番号・モーター番号の検索結果が一致すること。

差分が0であることを確認するまで、読み取り元切替や本番移行は行わない。

### この結果の読み方と注意点

- 実進入・着順・本番STは、両テーブルに値がある693行で不一致がなかった。
- 実進入と着順は各6行をフィールド単位で補える候補がある。

- 主テーブルのF判定617行は補完で上書きしない。Fは「数値が欠けた」という意味ではなく、記録上の重要な状態として保持する。

- 取得元と取得時刻は今回確認した行で欠損なし。ただし、値の正しさや提供元の意味的な同等性まで証明するものではない。
